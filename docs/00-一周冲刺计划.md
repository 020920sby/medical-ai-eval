## 三条实验设计原则（来自头痛 case 的教训）

1. **样本区分度优先**
   明确恶性区的样本测不出差异（胸痛 case 三家趋同），只有**良性-恶性模糊区**的样本才有横评价值。每条样本记录「三家是否分化」。

2. **每一轮用户原话必须归档**
   头痛 case 里 Round 2 自己说了什么没有原文 → 无法复核，也无法证明对比公平。
   **`test-records` 必须包含每一轮的 user 原文。**

3. **结论必须晚于筛查**
   阿福在头痛 case 里先给了「更像是紧张型头痛」再筛查 → 判定为 **先归因后筛查**，不是"被话术带偏"。

### D1 · 评测框架地图（5h）← **立即开始**

**上午 · 通用评测框架**

- 读 `lm-evaluation-harness`：理解 task / prompt / few-shot / metric / aggregation / `--log_samples`
- 建通用 benchmark 地图：C-Eval / CMMLU / HumanEval / AGIEval / HELM

核心认知（面试要能脱口而出）：

> **C-Eval 是"考什么"，lm-evaluation-harness 是"怎么统一组织考试"。**
> 它们都是**能力考试**，不是**安全评测**。

**下午 · 医疗评测框架**

- **HealthBench 深读**（这是 rubric-based 多轮评测的标杆，也是百川/蚂蚁的战场）
  - 5,000 段多轮对话 · 262 名医生 · 60 国 · 48,562 条 rubric
  - 五个轴：`completeness 39%` / `accuracy 33%` / `context_awareness 16%` / `communication 8%` / `instruction_following 4%`
  - 变体：Consensus（仅保留医生共识项）/ Hard（o3 最高才 32%）/ meta_eval（验证 judge 与医生一致性）
  - 机制：单条 rubric 可给**负分**（惩罚项）；聚合分数 clip 到 [0,1]；**bootstrap 重采样给置信区间**
- 中文医疗评测集：CMB / CMExam / CBLUE / MedBench / **SuperCLUE-MedAssist**
- **对标分析**：我的 rubric vs HealthBench（切分方式不同：你按临床场景，它按能力维度——这是互补，不是替代）

**产出**

- `docs/20-评测集与框架地图.md`
- `docs/21-rubric对标HealthBench.md`
- 面试话术：3 个必答题的答案

**验收**

- [ ] 不看资料能画出 C-Eval / harness 关系图
- [ ] 能说出我的 rubric 与 HealthBench 的 3 个差异
- [ ] 能说出 SuperCLUE-MedAssist 的结论（8 款产品平均 56.40，报告解读 43.76 是普遍弱项）

### D2 · 样本定稿 + L2 人工对齐（6h）

**上午 · 30 条样本定稿**

从现有 60+ 候选里筛，按 rubric 权重大致配比：

| 场景 | 条数 | 权重 |
|------|------|------|
| 急症/危重症识别 | 9 | 30% |
| 用药安全 | 9 | 30% |
| 报告解读 | 5 | 18% |
| 导诊/分诊 | 4 | 12% |
| 慢病管理 | 3 | 10% |

铁律：**这一步不做医学打磨**，只判断"这条能不能测"。

**下午 · L2 人工对齐测试**

1. 挑 20 条，**人工**判每条期望的最终建议（EMERGENCY / OUTPATIENT / HOME / UNCLEAR）
2. 与 `l2_evaluator.py` 的 `final_triage` 逐条比对
3. 算一致率；不一致的归因：L2 bug 还是已知边界
4. 真 bug → 加进 `SELFTEST_CASES`（只增不删）

**产出**：`data/samples/` 30 条 + **L2 人工一致率 X%** + 不一致清单

**验收**：`python3 l2_evaluator.py --selftest` 仍 10/10

### D3 · 百川批量抓包评测（6h）

**上午 · 打通批量**

1. Burp 里导出**请求体**（当前只有响应，没有用户原话）
2. 提取 `Cookie` / `Authorization` / 请求头
3. 写 Python 重放脚本，只替换 query 字段，**限速 8–10 秒/次**

**下午 · 跑数据**

- 30 条 × **3 次重复采样** = 90 次调用
- 为什么跑 3 次：报**方差**。SuperCLUE 测了稳定性，大多数第三方评测做不到

**产出**：`data/test-records/baichuan/` 90 条 + 方差数据

**验收**：每条含 query 原文 + 完整响应 + trace + 引用 + 3 次结果

⚠️ **边界**：报告和公开材料中**不出现**百川的内部 API 端点、字段结构、内部工具名。

### D4 · 小荷人工多轮 20 条（6h）

**应答卡机制**：每个样本配一张卡——产品问到某个维度，就照卡上对应槽回答；**没问到的绝不主动说**。

> 这样"追问质量"才可对比：问得全的产品拿到关键信息，问不全的产品在信息缺失下给了什么建议，那才是风险所在。

- 小荷 20 条多轮实测
- **每一轮的用户原话必须记录**
- 同日发起：请研究生朋友抽检 10 条高风险样本

**产出**：`data/test-records/xiaohe/` 20 条

### D5 · 阿福人工多轮 20 条 + L3 Judge 校准（6h）

**上午 · 阿福 20 条**（同一套应答卡，保证可比）

**下午 · L3 LLM-as-Judge**

1. 用 rubric 写 judge prompt
2. 对百川 90 条 + 小荷/阿福 40 条跑自动评分

**产出**：阿福 20 条 + **L3 人工一致率 X%** + L2/L3 冲突清单

### D6 · 双轨对比 + ortho-rehab 闭环（6h）

**上午 · 通用 benchmark 副轨**（time-box 2 小时）

- 装 `lm-evaluation-harness`，跑 C-Eval 子集（`--limit 100`）
- 超时则降级为轻量实现，并**如实记录为什么降级**

→ 产出**并列表**：C-Eval 通用能力分 ✕ 医疗安全分。这是"通用 benchmark ≠ 医疗安全"的**实证**。

**下午 · ortho-rehab Agent 闭环**

- 用同一套 rubric 评自己的 Agent
- 找 3–5 个问题 → 改 → 复评
- 这是唯一能展示「**评测 → 产品改进**」闭环的样本

**产出**：双轨并列表 + 闭环记录

**下午 · 作品集 + 话术**

8–12 页 PDF + 简历改写 + **12 个预判问答**，必含：

2. 你怎么保证评分一致性？→ 行为化锚点 + 0 分必写理由 + 医学抽检

6. 你的评测和 HealthBench 差在哪？
7. 为什么通用 benchmark 不够？→ 双轨并列表
8. 多轮怎么评？→ 结构类可程序化（升级延迟/信息遗忘/建议漂移），体验类人工
9. 追问质量怎么量化？→ 高低价值问题分层
10. 你的规则层边界在哪？→ 已知边界清单（3 条）
11. 你怎么处理抓包的合规边界？
12. 你的评测有什么局限？
